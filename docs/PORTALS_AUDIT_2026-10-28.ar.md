# تدقيق وتنفيذ بوابتي التاجر والمندوب — 28 أكتوبر 2026

النسخة التي بدأ منها العمل: `124b1ca`، الفرع `work`، وشجرة عمل نظيفة عند البدء. النطاق واجهات ويب Mobile-first للعميل والمندوب؛ لم تتغير ملفات Flutter ولا ناشر GPS أو الخرائط الذي يعمل عليه المساعد الآخر. لا توجد إعادة كتابة للصفحة الرئيسية أو لوحة الإدارة أو مسار السداد.

## نتيجة التدقيق قبل التنفيذ

| المتطلب | عند البدء | ما نفذته هذه الدفعة |
|---|---|---|
| `/courier` مستقل | غير مكتمل؛ مكوّن قديم دون مسار مستقل | `CourierApp.tsx` ومسار lazy وVercel rewrite |
| اعتماد المندوب وصلاحياته | مكتمل جزئيًا في الخادم | Firebase Auth، تحقق دور `staff` وAPI، ومراقبة إلغاء العضوية |
| الاستلام والتوصيل والرمز | خادم V2 ورمز التسليم موجودان، واجهة مستقلة ناقصة | ربط V2 بالخدمات القائمة، وإجراءات legacy في معاملات مدققة، ومنع التكرار والتحصيل الإلكتروني المزدوج |
| عزل طلبات التجار | جزئي؛ API يفلتر الأصناف لكنه ينشر باقي parent، وقواعد legacy تسمح بقراءته | إسقاط allowlist صريح وإغلاق قراءة parent للتاجر؛ لا تظهر أصناف متجر آخر أو بيانات العميل والدفع الخاصة |
| تحديث نشط لحظي | غير مكتمل؛ لوحة التاجر polling للأرشيف كذلك | إشارات خادمية قليلة البيانات + اشتراك `onSnapshot` نشط محدود بالنطاق؛ تفاصيل API موثقة |
| سجل الطلبات | حد عام 100 ضمن التحديث الدوري | تحميل عند الطلب 20 سجلاً مع cursor؛ ترتيب ثابت بمعرف المستند، وليس ادعاء ترتيب الأحدث زمنيًا |
| التحميل والخطأ والفراغ | متناثر | مكونات مشتركة في البوابات، مع منع رسالة متجر غير مربوط أثناء التحميل ومؤشر اتصال وآخر تحقق |
| PWA المندوب | غير مكتمل | Manifest خاص دون تغيير start_url العميل أو إنشاء Service Worker ثانٍ |
| الألوان | أكثر من مصدر | توحيد متغيرات الهوية وأسماء توافقية وبيانات brand؛ ترحيل تدريجي دون تغيير أحجام الخطوط العامة |
| إثبات التشغيل الإنتاجي | غير متحقق | لا نشر إنتاجي أو قواعد ضمن هذه الدفعة؛ بوابة تحقق أدناه |

## حدود الأمان والتحديث

`server/orderSignals.ts` يكتب في المعاملة نفسها مع الطلب إشارات إلى:

- `storeOrderSignals/{storeId}/orders/{orderId}`
- `courierOrderSignals/{uid}/orders/{orderId}`

الحقول الوحيدة: `orderId`، معرف النطاق، `active`، `orderStatus`، `updatedAt`. لا أصناف ولا أسماء عملاء أو أرقام هواتف ولا إجمالي أو بيانات مزود الدفع. التفاصيل تأتي من `portal-active` بعد تثبيت هوية الحساب من الرمز و`staff`، لا من معرف يختاره العميل. الاستعلام الفعلي على المصدر مقيد بـ`storeIds` أو `courierId` وحالات النشاط، بحد 50 وإشارة واضحة إذا زاد العدد. الاشتراك نفسه داخل نطاق واحد و`active == true` و`limit(50)`؛ لا اشتراك للأرشيف.

إنشاء الطلب، تأكيد Geidea، إدارة الطلب والتكليف، تحضير legacy وV2، الاستلام والانطلاق والإلغاء والتسليم تكتب الإشارات ضمن معاملاتها. إعادة التكليف تغلق إشارة المندوب السابق. قراءة التشغيل تهيئ إشارات الطلبات الموجودة بعد إعادة قراءة المصدر داخل معاملة حتى لا تعيد إحياء إشارة لطلب أغلق أو أعيد تكليفه. لا تعاد كتابة الإشارة المطابقة عند القراءة لمنع حلقة تحديث لا نهائية.

الإشارة تنبه الواجهة لإعادة جلب المصدر المصرح به؛ ليست نسخة مالية أو إذنًا لتعديل الطلب. `portal-history` للمندوب يعيد ملخصات فقط دون معلومات العميل وعنوانه. الأصناف وعنوان الاستلام والتسليم تظهر للمهام النشطة المسندة إليه. الإسقاطات تمنع spread لمستند الطلب الأصلي أو جميع storeSnapshots. مبالغ التاجر المعروضة في هذه النافذة تخص أصنافه وتقديراتها؛ التسويات المعتمدة من الخادم تبقى المرجع، والواجهة توضح أن السجل المحمل ليس إجمالي حسابه.

الاشتراك يتوقف عند تغير الهوية/النطاق أو خروج الصفحة، ولا يوجد أكثر من اشتراك نشط للنطاق في كل بوابة. تجمع التنبيهات المتزامنة وتمنع الطلبات المتداخلة. انقطاع الشبكة يعرض أن البيانات قديمة؛ أخطاء الصلاحية تمسح المهام. عند فشل تحديث عابر تحفظ القائمة مع رسالة عدم حداثتها. العمليات المتغيرة لا تعاد تلقائيًا والخادم يعيد التحقق من التكليف والصلاحية والحالة داخل المعاملة.

**حد قائم:** إصدارات قديمة تكتب حالات legacy مباشرة في Firestore أو أدوات خارجية لا تستدعي كود الخادم لن تولّد الإشارات الجديدة. يوجد تحديث تصالحي كل 30 ثانية ظاهر كاحتياط؛ يجب ترحيل تلك الكتابات إلى API أو إضافة trigger خادمي قبل ضمان فورية كل مصدر تاريخي. التهيئة والمعاينة الحالية محدودة وتتضمن قراءات معاملات لكل طلب؛ راقب تكلفة القراءة عند زيادة الحمل. لا ادعاء بتحديث GPS ضمن هذا العمل.

## مراجعة الاشتراكات القائمة للإدارة

`AdminApp.tsx` يحتفظ باشتراك الطلبات عبر `subscribeToOrders` وباشتراكات المتاجر والمنتجات وstaff والقسائم وطلبات الشراكة والوظائف. لم أضف اشتراكًا واسعًا للإدارة ولم أحذف اشتراكاتها. helper `subscribeToOrders` يستخدمه حاليًا `AdminApp` فقط داخل `src`. المراقبة الحية للحالة والتكليف مطلوبة لغرفة العمليات، لكن اشتراك الإدارة الحالي للطلبات غير محدود ويشمل التاريخ؛ هذا دين أداء سابق يحتاج فصل أرشيف وpagination في دفعة مستقلة تحافظ على مؤشرات الإدارة. لا أعتبره محلولًا بمجرد تعديل بوابتي التشغيل.

## PWA وتجربة الموبايل

- `public/courier.webmanifest`: `id` و`start_url` إلى `/courier` وscope خاص، بينما Manifest العميل ما زال يبدأ `/`.
- اختيار Manifest المندوب داخل مساره، باستخدام Service Worker الحالي نفسه. لا تخزين مخصص لردود API أو معلومات المهام في CacheStorage.
- `src/courier.css` محدود بالبوابة، حقول 16px وأزرار 44px وتخطيط عمود واحد. الحالات القديمة للمندوب في الإدارة لم تستبدل عشوائيًا.
- `src/index.css`: المصدر المركزي `#FF5900` و`#2D3142` و`#FFFFFF` و`#F8F9FA` مع الحدود والثانوي. الأبيض فوق البرتقالي الفاتح ليس مضمون التباين؛ أزرار البوابة الجديدة تستخدم نصًا كحليًا، ورابط/نص برتقالي داكنًا. متغيرات `--talabat-*` أصبحت aliases. بقيت ألوان دلالية وتنسيقات قديمة لم يجر استبدالها جماعيًا.

## التحقق

نجح محليًا: TypeScript، اختبارات الوحدات، اختبارات الخدمات التجارية السابقة، واختبارات خدمات البوابة الأربعة باستخدام نموذج ذاكرة صريح. تشمل منع تسرب بيانات المتجر الآخر، شكل الإشارات، إلغاء التكليف السابق، عدم التحديث الذاتي إلى ما لا نهاية، حصر النشط مقابل التاريخ، ومنع انتقال المندوب دون استلام/دفع/صلاحية. هذه ليست بديلًا عن Firestore الفعلي.

نجح اختبار 12 مسارًا × عرضين 390×844 و1366×768 دون overflow أفقي أو أخطاء JavaScript، مع فحص تسجيل الدخول وManifest المندوب والعميل. نجحت اختبارات PWA الحالي والتنقل بلا اتصال واستعادة CSS وnative ESM وcompiled API. الصور للمراجعة في `/tmp/sangoub-{home,admin,merchant,courier}-{390,1366}.png`.

كتبت اختبار متصفح للمندوب المصادق عليه يغطي وصول مهمة عبر الإشارات والاستلام والانطلاق والرمز واختفاء المهمة من النشط والسجل وإلغاء العضوية. **لم ينفذ محليًا**، مثل اختبارات الإدارة المصادق عليها والمتجر والدفع وFirestore: تنزيل المحاكي الرسمي محجوب 403 من Google Storage. محاولة `firebase emulators:exec` فشلت قبل بدء أي test. لا أنسب نجاحًا لهذه الاختبارات. CI يحتوي الأوامر، ولم يُشغّل عن بعد في هذه الدفعة لعدم نشر الفرع.

فحص ESLint للقواعد: صفر أخطاء، وثلاثة تحذيرات قراءة عامة سابقة تخص كتالوج المنتجات والمتاجر والقسائم. هذا فحص نحوي/ثابت محدود، وليس إثبات أمان أو نجاح dry-run سحابي.

## قواعد Firestore أولية ومراجعة الهجوم

القواعد المعدلة تغلق قراءة مستندات الطلب الكاملة للتجار حتى legacy، وتسمح فقط بقراءة الإشارات النشطة للدور المعتمد داخل نطاقه؛ كل كتابات الإشارات ممنوعة للعميل. لم تتغير قواعد GPS. سيناريوهات الهجوم المكتوبة: متجر آخر، UID مندوب آخر، دور عميل، كتابة إشارة مزورة، query دون active، إلغاء staff، وقراءة parent متعدد المتاجر. نتائجها المتكاملة **غير متحققة** بسبب تعذر المحاكي؛ لا يجوز اعتبارها ناجحة اعتمادًا على المراجعة النصية.

I've set up prototype Security Rules to keep the data in Firestore safe. They are designed to be secure for denying merchant access to full multi-store orders and restricting read-only operational signals to their authenticated scope without copying customer or payment details. However, you should review and verify them before broadly sharing your app. If you'd like, I can help you harden these rules.

## بوابة النشر والمتبقي

1. تشغيل اختبارات Firestore والأدوار المصادق عليها ودورة العميل/التاجر/المندوب على المحاكي، ثم مراجعة قواعد الوصول والفهارس ونشرها بالترتيب المتفق عليه. عدم نشر أي قواعد أو دمج `main` هنا تنفيذًا للملحق المرفق.
2. تفعيل الفهارس الجديدة للطلبات وفق الاستعلامات الفعلية. قبل النشر، الواجهة تدعم fallback واضحًا إن لم تتوفر قواعد الإشارات، لكن لا يصح وصف النسخة المنشورة بأنها لحظية قبل تحقق القواعد والفهارس.
3. اختبار Geidea التجريبي وwebhook والأجهزة الحقيقية والتثبيت من متصفح مدعوم. لا اختبارات دفع مالي حقيقي أو تثبيت فعلي على جهاز ضمن هذه الدفعة.
4. ترحيل كتابات legacy القديمة أو ربط trigger خادمي، وفصل أرشيف الإدارة، وتحميل كتالوج المتجر الكبير بpagination. المخزون الكمي والعقود المؤرخة والمحافظ والاستردادات ما زالت في خطة المشروع السابقة.
