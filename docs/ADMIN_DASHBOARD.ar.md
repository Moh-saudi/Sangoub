# تشغيل لوحة الإدارة

الواجهة الجديدة في `feature/real-orders-auth-maps` وتفتح من `/admin`؛ الصفحة `/` موقع تعريفي عام للعملاء والشركاء. بوابة الإدارة مستقلة دون محاكي أو حسابات تشغيل موبايل. تستخدم Firebase Authentication وFirestore، ولا تنشئ حساب مدير أو منتجات وأسعارًا افتراضية. يجب أن يكون للحساب الحقيقي وثيقة `admins/<Firebase UID>` أضافها مسؤول المشروع. القواعد المنشورة تتحقق من الوثيقة؛ حفظ `role: admin` في المتصفح لا يمنح صلاحية.

## المنتجات والمتاجر

1. افتح «المنتجات والمتاجر» ثم «المتاجر» → «إضافة متجر». أدخل الاسم والنشاط والتصنيف والعنوان ورسوم التوصيل والحد الأدنى. المتجر الجديد مغلق افتراضيًا حتى تختار فتحه.
2. افتح «المنتجات» → «إضافة منتج». اختر متجره وأدخل الاسم والوصف والسعر والتصنيف، ثم ارفع صورته أو أدخل رابط HTTPS لصور تملكون حق استخدامها. يمكن إضافة السعر قبل الخصم والشارة وإظهاره ضمن المنتجات المميزة.
3. «تعديل» يفتح بيانات المنتج الحالية لتعديلها وصورته. يبقى المتجر ثابتًا للصنف الموجود، وتُحفظ خياراته السابقة التي لا يعدلها النموذج. السعر قبل الخصم الفارغ يعني عدم وجود خصم معلن؛ يجب ألا يقل عن سعر البيع.
4. التوافر يمكن إيقافه وتفعيله. «أرشفة» تخفي الصنف من المنيو وتمنع إنشاء طلبات جديدة له، دون حذف تفاصيل طلباته السابقة. «استعادة» تعيده غير متاح؛ فعّله عندما يصبح جاهزًا للبيع.
5. ابحث بالاسم أو المتجر أو الوصف، وصفِّ بالمتجر والتصنيف والتوافر، ورتّب بالاسم أو السعر أو الكميات المسلّمة.

لكل صنف كميات مسلّمة وقيد التنفيذ، وقيمة أصنافه المسلّمة حسب لقطة السعر عند الطلب، بما فيها الإضافات وقبل خصم القسائم ورسوم التوصيل. لا تُحسب الطلبات الملغاة. البيانات مبنية على سجلات الطلبات المتاحة، ولا تُستنتج أصناف من ملخص قديم مفقود التفاصيل. هذا ليس نظام مخزون كمي؛ `inStock` توافر يدوي ولا يمثل رصيد قطع.

رفع الملفات الفعلي يحتاج إعداد R2 والخادم الموثق في [R2.ar.md](R2.ar.md). تعديل النصوص والأسعار أو استخدام رابط صورة قائم يتم عبر Firestore من جلسة مدير، دون المرور بخدمة رفع الملفات. لا تُرسل مفاتيح R2 إلى المتصفح.

## الفريق والخصومات

- من «الفريق والخصومات» أضف UID لحساب حقيقي مسجل، وحدد دور المندوب أو مدير المتجر، وبياناته والمتجر المسؤول عنه. يمكن تعديل السجل من القائمة أو إلغاء صلاحية الموظف. لا يتم حذف حساب Firebase Authentication أو طلباته. واجهة الإلغاء تمنع سحب صلاحية مندوب له طلبات نشطة قبل إعادة تعيينها.
- أضف كود خصم ثابت بالجنيه أو نسبة حتى 100%، وحدًا أدنى للطلب ووصفًا. القائمة تدعم تعديل الكود الحالي أو حذفه؛ معرف الكود ثابت أثناء التعديل. حذف الكود لا يغيّر إجماليات الطلبات السابقة.
- إنشاء المدير الرئيسي ما زال من حساب مسؤول Firebase فقط. لا توجد كلمة مرور أو شخصية مدير افتراضية.

## الطلبات والمطبخ والعمليات

«الطلبات والتقديمات» تعرض الطلبات وطلبات الشراكة والتوظيف. يمكن البحث برقم الطلب أو اسم العميل أو الهاتف، والتصفية بالوزارة والحالة بما فيها الملغاة. يُعين المدير مندوبًا لطلب جاهز أو يعيد تعيينه وهو في الطريق، ويمكن إلغاء طلب غير نهائي بعد تأكيد الإلغاء. الانتقالات تنتظر حفظ الخادم وتعرض الأخطاء. التسليم النهائي يتم بواسطة المندوب برمز العميل والتحصيل عبر API.

تستمر شاشة المطبخ والعمليات الحية الموضحة في [WEB_MOBILE_INTEGRATION.ar.md](WEB_MOBILE_INTEGRATION.ar.md). إحصاءات التسليم اليومية تستخدم توقيت القاهرة ووقت التسليم الموثق.

## التجربة المحلية

```bash
npm install
npm run dev
```

افتح `http://localhost:3000/admin` على الجهاز الذي شغّلت عليه المشروع. لإعداد خدمات الخادم الحقيقية، ضع الأسرار في `.env.local` داخل المشروع؛ الخادم يدعم تحميله محليًا، وملفات البيئة مستبعدة من Git. لا تحتاج إضافتها إلى Vercel لتجربتها على جهازك. اختبارات المحاكيات لا تحتاج مفاتيح إنتاج.

تجربة المتصفح المنفذة على مشروع `demo-capital-talabat` المعزول شملت إنشاء متجر وصنف، حفظ السعر ثم قراءته من Firestore، التوافر والأرشفة والاستعادة، البحث، حفظ الخصم، رفض الكتابة بعد سحب الإدارة، وأحجام 390/768/1440. الصور المرفوعة إلى حاوية R2 الحقيقية لم تُختبر لغياب إعداداتها السرية من بيئة الوكيل؛ لم تُضف منتجات أو بيانات اختبار إلى مشروع الإنتاج.


اختبار بوابة الإدارة الكامل: نفّذ `npx playwright install chromium` مرة واحدة ثم `npm run test:admin-web` مع Java 21. الاختبار يبدأ محاكيات Auth وFirestore ويختبر رفض الأدوار الثلاثة ودخول المدير والسحب الحي للصلاحية والحفظ من الواجهة. يستخدم مشروع demo معزولًا ويرفض العمل خارج المحاكيات المحلية. في هذه البيئة استخدم `CHROMIUM_PATH=/usr/bin/chromium` لاستعمال Chromium الموجود.


## تحديث تجربة الإدارة — ٢٢ أكتوبر ٢٠٢٦

- قائمة جانبية للأقسام على الكمبيوتر وقائمة قابلة للفتح والإغلاق على الموبايل، مع حفظ القسم المختار في رابط الصفحة.
- مركز العمليات يعرض يوم القاهرة والجهة والمؤشرات اليومية ومسار حالات الطلبات. اختيار حالة يعرض الطلبات النشطة من جميع الأيام، بينما العرض الافتراضي يعرض طلبات اليوم المختار.
- البحث يشمل رقم الطلب والعميل والهاتف والوزارة. تظهر أحدث ثمانية طلبات في الملخص، وتتوفر الإدارة الكاملة في قسم الطلبات والتقديمات.
- توزيع الجهات قابل للتوسيع، وحالات الفراغ تقود لإضافة المتجر والفريق. لا تظهر خرائط أو مواقع أو نسب إنجاز افتراضية.
- جميع المؤشرات والعدادات مصدرها الاشتراكات الحالية؛ تغييرات التصميم لا تمنح صلاحيات ولا تغيّر قواعد الأمان أو عقد Flutter.


راجع [إدارة المستخدمين وسجل التدقيق ونشر القواعد الجديدة](USERS_AND_AUDIT.ar.md). تعديلات الويب الإدارية تمر الآن عبر `/api/admin-users` و`/api/admin-data` لضمان تسجيلها؛ لا تستخدم كتابة Firestore مباشرة من حساب المدير.

## الترتيب المدمج المعتمد — ٢٢ أكتوبر ٢٠٢٦

شريط علوي نحيف ببحث فعلي (`Ctrl+K`) في الأقسام والطلبات والعملاء المرتبطين بها والمتاجر والمنتجات المتاحة في الاشتراكات الحالية. اختيار نتيجة ينقل إلى القسم ويطبق البحث. القائمة الجانبية مجمعة حسب التشغيل وإدارة المنصة والرقابة، وتدعم الطي على الكمبيوتر مع حفظ تفضيل العرض محليًا فقط.

شاشة الطلبات أصبحت جدولًا بأعمدة للعميل والجهة والأصناف والقيمة والحالة والمندوب والتوقيت، ورأس ثابت داخل مساحة التمرير. فتح «تفاصيل وإدارة» يظهر لوحة جانبية حية فيها الإجراءات الموجودة والتحضير والتعيين والخريطة. المستخدمون والتدقيق والتحرير يستخدمون لوحات جانبية أيضًا. تظهر حالات الطلبات بعناوين مختصرة داخل الجداول. الواجهة تتكيف مع الموبايل، والجداول العريضة تمرر داخل حدودها دون توسيع الصفحة. لا تغيير في الصلاحيات أو عقد البيانات بهذا التحديث.


راجع [الفرق بين استضافة الموقع وR2 وFirebase وتشخيص النسخة المنشورة](HOSTING_AND_STORAGE.ar.md). التنفيذ الداخلي للواجهات موجود الآن في `server/handlers/`، مع بقاء عناوين `/api` كما هي.

### تصميم الكتالوج

المنتجات والمتاجر تُعرض في جدول مدمج افتراضيًا، مع خيار البطاقات و25 نتيجة في الصفحة. التصفية والبحث يعيدان الصفحة إلى البداية، ويُعرض عدد النتائج ومسح التصفية. عند عدم وجود متجر، تظهر خطوة إضافة أول متجر. يعرض الجدول حالة التوافر والأرشيف ويحتفظ بإجراءات التعديل والإيقاف والاستعادة؛ المبيعات من الأصناف المسلّمة وليست مخزونًا فعليًا.

المحرر الجانبي له عنوان وأزرار حفظ ثابتة أثناء التمرير. يمكن معاينة ملف الصورة وإزالته قبل الحفظ؛ الإزالة هنا تلغي الاختيار المحلي فقط. الاختبار عبر المتصفح يشمل التنقل بين الصفحات وتصفية المنتجات وتحديث التوافر ومعاينة الصورة ومقاسات الهاتف والكمبيوتر، في محاكيات محلية معزولة.

### نسخة الموقع العام على الموبايل

الهيدر يعرض العلامة وزر التطبيق في صف واحد، والصورة قبل النص على الشاشات الصغيرة. البطاقات التعريفية قابلة للضغط لفتح نافذة «نكمل على التطبيق؟». تظهر معاينة محدودة من المتاجر المفتوحة والمنتجات المتاحة غير المؤرشفة من البيانات المشتركة، دون إنشاء بيانات في الإنتاج. لا تظهر منتجات المتجر المغلق في المعاينة.

تستخدم النافذة الرابط الرسمي الموجود في `VITE_MOBILE_APP_URL` عند إضافته، ويجب أن يكون HTTPS. حاليًا، لا يوجد رابط معتمد؛ تعرض النافذة انتظار الإصدار ووسيلة للاستفسار. يُعرض اسم المنتج أو المتجر المختار داخل النافذة فقط؛ فتح صفحة الصنف نفسه داخل التطبيق يحتاج اتفاقًا منفصلًا على روابط التطبيق، ولا يُفترض أنه مدعوم الآن.

### تكوين الموبايل الجديد

الهيرو يستخدم الصور الأربع المحدّثة لمنشآت الحي الحكومي: الحدائق والوزارات والمشهد البانورامي واللقطة الليلية. على الكمبيوتر تكون خلفية بتدرج يحافظ على قراءة النص وظل خارجي خفيف؛ وعلى الهاتف تُعرض الصورة كاملة بنسبة أبعادها الأصلية فوق عنوان مختصر وأزرار الطلب، دون قص المنشآت أو تغطيتها بالنص. يعمل السحب والأسهم والنقاط وإيقاف العرض، وتُحمّل الصور التالية بأولوية منخفضة لتقليل الانتظار عند الانتقال. هوية السنجاب تبقى في الشعار وزر التواصل العائم.

المتاجر والمنتجات صفان مستقلان قابلان للسحب يمينًا ويسارًا على الهاتف والكمبيوتر. تتحرك الصفوف تلقائيًا كل 4.5 ثوانٍ، وتعكس الاتجاه عند نهاية الشريط، وتتوقف في الخلفية أو مع تقليل الحركة وأثناء التركيز أو المرور. السحب والضغط على الأسهم يوقفان التشغيل التلقائي حتى يُشغله المستخدم من الزر. لا تُكرر البطاقات لعمل حركة وهمية. المنتج الوحيد يملأ الصف دون مساحة فارغة، ولا تُعرض أسهم غير لازمة له.

خطوات الطلب الثلاث بطاقات في صف واحد حتى على الهاتف. زر السنجاب عائم فوق شريط الطلب ويختفي مع الشريط عند فتح نافذة التطبيق، ولا يُدمج داخل شريط الطلب. القائمة للموبايل تُغلق باختيار الرابط أو الضغط خارجها أو Escape. خط الصفحة العامة `Cairo Web` داخل الموقع، وترخيصه في `public/fonts/Cairo-OFL.txt` ومصدره [Google Fonts Cairo](https://github.com/google/fonts/tree/main/ofl/cairo).

الفوتر يعرض أيقونات واتساب والبريد بروابطهما الفعلية، وأيقونات فيسبوك وإنستغرام وتيك توك ظاهرة حسب طلب المالك، دون روابط تخمينية. لتفعيل روابطها مستقبلًا اضبط متغيرات الويب العامة `VITE_SOCIAL_FACEBOOK_URL` و`VITE_SOCIAL_INSTAGRAM_URL` و`VITE_SOCIAL_TIKTOK_URL` بروابط HTTPS ثم أعد البناء والنشر. يظهر اعتماد التنفيذ `Mesk – Vlab` وحقوق `© 2026 Mesk – Vlab. All rights reserved.`؛ العلامة في الفوتر منسقة نصيًا بالألوان المرسلة. أيقونة تيك توك من [Simple Icons](https://github.com/simple-icons/simple-icons/blob/develop/icons/tiktok.svg) تحت CC0.

### التصفح والدعم والوظائف

خطوات «من المنيو لمكتبك» ثلاث بطاقات في صف واحد على الموبايل. يظهر زر Google Play بالشارة المعتمدة، ويفتح نافذة التطبيق لحين إضافة الرابط الرسمي. الدعم متاح من زر السنجاب العائم الذي يفتح واتساب إلى `201017799580`، فوق شريط الطلب على الهاتف. الهوية والحركة وأصول تسليم الموبايل موضحة في `docs/MASCOT_IDENTITY.ar.md`.

شريط المتاجر المفتوحة يعرض بطاقات صغيرة، مع السحب والأسهم والحركة التدريجية ذهابًا وإيابًا كل 4.5 ثوانٍ. يمكن إيقاف الحركة من زر مخصص، وتتوقف أثناء التفاعل وإخفاء الصفحة وتفضيل تقليل الحركة. لا تُنشأ متاجر تجريبية في الموقع.

مدخل الوظائف برمز سكوتر يقود إلى `/careers`، وهي صفحة للاستفسار عن فرص فرق التوصيل والمطبخ والتشغيل عبر واتساب، دون ادعاء توافر شواغر أو إرسال طلب توظيف محفوظ في قاعدة البيانات. توافر الوظيفة وشروطها يؤكده الفريق.

### قائمة خدمات السنجاب

الضغط على السنجاب يفتح قائمة مدمجة بثلاثة اختيارات: الدعم، طلب فطار، وطلب سوبر ماركت. الدعم والسوبر ماركت يفتحان واتساب مباشرة، والفطار يفتح معالج الأصناف والكميات وبيانات العميل والمراجعة قبل تجهيز رسالة واتساب. لا تُرسل الرسالة تلقائيًا ولا تُسجّل طلبات خادم من القائمة. يُعاد التركيز إلى السنجاب عند الإغلاق، وتُقفل خلفية الصفحة أثناء فتح القائمة. اختبارات المتصفح تغطي الخيارات والروابط ومقاسات الهاتف والوضع الأفقي والإغلاق بالضغط خارج القائمة وبـEscape، وتختبر فتح المسودة باعتراض واتساب محليًا دون تواصل فعلي.

اختيار الفطار أصبح معالج أصناف وكميات، مع الجمع بين الساندوتشات والوجبات والكشري ثم الاسم والعنوان واختيار كاش أو إنستا باي ومراجعة الرسالة. [تفاصيل المعالج والحدود والاختبارات](MASCOT_IDENTITY.ar.md#تجهيز-طلب-الفطار-عبر-السنجاب). الدعم والسوبر ماركت يحتفظان بمسار واتساب المباشر.

## عدد زوار الموقع

من قسم التسويق اختر «عدد الزوار» أو افتح `/admin#visitors`. تعرض الصفحة إجمالي المتصفحات الفريدة منذ بدء العدّ، والمتصفحات الفريدة خلال اليوم بتوقيت القاهرة، وزر تحديث يدوي. لا تشمل تطبيق الموبايل أو الزيارات التاريخية قبل نشر العدّ.

يستخدم الموقع معرّفًا عشوائيًا محفوظًا في المتصفح دون اسم أو رقم هاتف أو عنوان IP في بيانات الإحصائيات. الخادم يحفظ بصمة SHA-256 للمعرّف وآخر يوم زيارة، ويزيد العدادات ذريًا مرة واحدة لكل متصفح في اليوم. لا يزيد تحديث الصفحة أو إعادة إرسال الطلب العدد. تخزين المتصفح المحظور أو المحذوف والأجهزة المختلفة قد تؤثر على تقدير الزوار؛ هذا عدّ تقريبي وليس إثباتًا لهوية الأشخاص أو طلباتهم. تُتجاهل برامج الروبوت المعروفة من ترويسة المتصفح، ولا يضمن ذلك استبعاد كل الزيارات الآلية.

`POST /api/visitors` يسجل الزيارة فقط عبر JSON من نفس المصدر، ولا يعرض العدد. `GET /api/visitors` يعرض الأعداد للإدارة بعد التحقق من الجلسة والصلاحية. البيانات في `siteVisitors` و`siteMetrics` و`siteMetricDays` عبر الخادم فقط، وتخضع لمنع الوصول الافتراضي في قواعد Firestore. لا توجد خدمة تحليلات خارجية أو إعداد مطلوب. يفشل العدّ بهدوء ويعيد المحاولة دون تعطيل الطلبات.

التحقق: `npm run test:visitors` مع محاكيات Firebase، و`npm run test:admin-web` للتحقق من التسجيل الفعلي من المتصفح، ومنع تكرار العدّ، وعرض الصفحة للإدارة.

### مصادر الزيارات والتفاعل مع سنجوب

تعرض صفحة «عدد الزوار» آخر سبعة أيام (اليوم مشمول، بتوقيت القاهرة)، ومصدر أول زيارة مسجلة للمتصفح في كل يوم، وإجراءات سنجوب: الفتح اليدوي أو التفاعل مع دعوة الفطار، اختيار الخدمة، مراجعة الطلب، وضغط واتساب للفطار أو السوبرماركت أو دعم سنجوب. مجرد ظهور الدعوة التلقائية لا يزيد «فتح سنجوب». كل إجراء يحتسب مرة واحدة لكل متصفح يوميًا، وتُحفظ أعلام اليوم فقط في سجل المتصفح المجهول، والعدادات اليومية المجمعة في `siteMetricDays`.

نسب الإجراءات = مجموع الأعداد اليومية للإجراء خلال الفترة ÷ مجموع أعداد الزوار اليومية خلال الفترة. قد يتكرر المتصفح في أيام مختلفة، وقد يختار الخدمتين؛ لا تجمع نسب الصفوف ولا تعتبرها عدد أشخاص أسبوعيًا أو طلبات مؤكدة. الضغط على واتساب لا يثبت إرسال الرسالة أو اعتماد الطلب. التسجيل بأفضل جهد، وقد تفوت أحداث عند انقطاع الشبكة أو إغلاق الصفحة.

تصنيف المصدر محدود إلى فيسبوك وواتساب وإنستغرام والبحث ومواقع أخرى ومباشر/غير معروف؛ لا تُخزن روابط الإحالة أو قيم UTM الخام. يأخذ `utm_source` الأولوية ثم نطاق الإحالة، ويحفظ التصنيف فقط داخل جلسة المتصفح لليوم. تتوفر روابط نسخ جاهزة لفيسبوك وواتساب. بعض التطبيقات تحذف الإحالة، لذلك لا يمكن ضمان معرفة المصدر دون رابط موسوم. لا يوجد تفصيل حسب الجروب في هذه المرحلة.

الإجمالي السابق محفوظ. عند أول زيارة بعد التحديث يُستكمل مصدر زائر اليوم القديم دون زيادة عدد الزيارات. الزيارات التي لم يصنّف مصدرها تظهر «زيارات قبل تصنيف المصادر»، والتفاعلات السابقة لا تسترجع. يسجل `analyticsStartedAt` بدء البيانات الجديدة. التحقق يشمل تزامن الأحداث وإعادة إرسالها وتوافق البيانات القديمة، والتصنيف الصحيح لنطاقات الإحالة، ومسار سوبرماركت حقيقي على المحاكي مع اعتراض واتساب دون إرسال رسالة فعلية.

## طلبات سنجوب المسجلة من الموقع

من «التشغيل اليومي ← طلبات سنجوب» أو `/admin#sangoub` تظهر طلبات الفطار والسوبرماركت الجديدة. يكتب العميل رقم تواصل مصريًا مع الاسم والعنوان والدفع المطلوب، ثم يراجع الطلب ويضغط «تسجيل الطلب ومتابعة واتساب». بعد نجاح الحفظ يظهر رقم الطلب ورابط واتساب الذي يحمل الرقم نفسه. تعذر التسجيل لا يفتح رابط إرسال الطلب، وإعادة المحاولة بنفس البيانات لا تنشئ سجلًا إضافيًا.

الأصناف والأسعار غير متصلة بعد بكتالوج تجار مؤكد؛ لذلك تُحفظ في `sangoubRequests` كطلبات تحتاج تأكيد التوفر والسعر، دون إجمالي مالي أو حالة دفع مؤكدة أو تكليف تحضير أو مندوب. لا تدخل إيرادات أو تقارير التسليم. يستطيع المدير تسجيل «جارٍ التواصل / أُغلقت المتابعة / ملغى» مع ملاحظة وتدقيق، مع رفض تحديث متزامن يستند إلى حالة قديمة. إغلاق المتابعة ليس إثبات تسليم أو تحصيل. تظل هذه المرحلة مدخلًا للطلبات، ويحتاج تحويلها إلى دورة المتاجر والمندوب تسعيرًا وربطًا حقيقيًا بمنتجات التجار.

الحفظ العام يمر عبر إجراء `sangoub-request` فقط في `/api/orders` مع فحص JSON والمصدر والبيانات والأصناف من قائمة الخادم وحد 10 طلبات لكل رقم تواصل خلال 24 ساعة. الهاتف غير موثق بOTP. الطلبات التشغيلية الأصلية تظل تتطلب جلسة Firebase. القراءة والمتابعة تمران عبر `/api/admin-data` بصلاحية إدارة. لا تُرسل بيانات العميل لإحصائيات الزيارات، ولا يُعرض سجل الطلبات للعامة، ولا توجد تعديلات في قواعد Firestore أو تطبيق الموبايل. الطلبات القديمة المرسلة بواتساب فقط لا تُسترجع.
