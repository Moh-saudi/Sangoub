# مراجعة لوحة التاجر والكتالوج العام — 29 أكتوبر 2026

المقصود المعتمد: التاجر يختار منتجًا من كتالوج عام مشترك، ولا يعيد كتابة تعريفه. هذه الوثيقة تفرّق بين الوضع الموجود والإصلاح الحالي والأقسام المقترحة التي لم تُبن بعد.

## نتيجة فحص الأقسام التسعة

| القسم المقترح | الموجود فعليًا | ما يزال مطلوبًا |
| --- | --- | --- |
| الرئيسية | حالة المتجر وبطاقات ملخص من الطلبات المحملة | صفحة مستقلة، مقارنة الفترات، بحث شامل؛ البيانات المحملة لا تمثل كل التاريخ |
| الطلبات | تذاكر حية وسجل بصفحات وتحضير مسموح وتفاصيل أصناف المتجر | فلاتر تاريخ وبحث أوسع؛ لا ينقل التاجر الطلب إلى التوصيل أو يغير صلاحيات المندوب |
| المنتجات | قراءة عروض المتجر من `products` وتعديل السعر والتوفر | عالجت هذه الدفعة اختيار المنتج العام بدل الإنشاء من حساب التاجر؛ الإدارة تعتمد التعريف |
| المخزون | توفر يدوي وأرشفة واستعادة العرض بحالة غير متاح | لا يوجد دفتر كميات أو حركات مخزون أو حجوزات |
| العملاء | لا توجد صفحة عملاء عامة للتاجر؛ بيانات الطلب مصفاة على الخادم | تصميم عرض بيانات الحد الأدنى اللازمة فقط، دون فتح مجموعة `users` أو بيانات متاجر أخرى |
| التقارير | أصناف أكثر مبيعًا وحسابات من الطلبات المتاحة | تجميعات خادمية للفترات المكتملة ومقارنة الأيام والشهور |
| المدفوعات | التاجر يرى تقديرات؛ التسويات المعتمدة تُدار إداريًا | كشف تسويات موثوق للتاجر، حالات الدفع ومراجعها؛ لا تكفي حسابات الواجهة لإثبات رصيد أو تحويل |
| الإعدادات | تغيير حالة المتجر ومدخل حساب واستعادة كلمة مرور | صفحة بيانات النشاط وساعات العمل والتفضيلات بصلاحيات منفصلة |
| الدعم | نافذة إرشادات ورابط دعم | لا يوجد نظام تذاكر ومتابعة حالاتها |

لم تُضف صفحات شكلية لتبدو الأقسام مكتملة. الموظفون والانضمام وبيانات النشاط وتفاصيل الطلب شاشات داخلية أو وحدات تحتاج نطاقًا منفصلًا.

## المصدر الواحد والفرق بين المنتج والعرض

- `catalogProducts/{catalogProductId}`: تعريف المنتج العام المعتمد: الاسم والوصف والتصنيف والصورة والخيارات، دون سعر متجر أو تكلفته أو عقده أو بيانات عملائه. التعريف في هذه الدفعة ثابت بعد الاعتماد؛ لا يوجد محرر نسخ/تعديلات عامة بعد.
- `catalogOffers/{sha256(storeId + NUL + catalogProductId)}`: علاقة فريدة بين المتجر والمنتج العام، تحفظ `productId` الخاص بعرض المتجر.
- `products/{productId}`: عرض المتجر المنشور، وفيه `catalogProductId` وسعر المتجر وتوفره وأرشفته. يحتفظ أيضًا بإسقاط منشور لحقول التعريف كي تظل قراءات الويب والموبايل الحالية ومعرّفات السلال والطلبات متوافقة. هذا إسقاط قراءة من تعريف معتمد واحد، وليس تعريفًا ثانيًا يحرره التاجر.
- `orders.items` ولقطات السعر عند الشراء لا تتغير بتغيير أسعار المتجر أو أرشفة عرضه.

لا نربط المنتجات المتشابهة بالاسم تلقائيًا: اختلاف العلامة أو الوزن أو العبوة أو الخيارات قد يعني منتجين مختلفين. لا تحذف هذه الدفعة أي منتج قديم أو طلب أو رابط مستخدم حاليًا.

## التشغيل والترحيل

1. من كتالوج الإدارة، اختر منتجًا قائمًا مكتمل البيانات واضغط «اعتماد بالكتالوج العام». يلزم تأكيد واضح لأن التعريف يصبح معتمدًا وثابتًا في هذه النسخة.
2. تنشئ المعاملة التعريف مرة واحدة، وتربط عرض المتجر الأصلي به **دون تغيير معرفه أو سعره**. تكرار الاعتماد لن ينشئ تعريفًا جديدًا.
3. مدير متجر آخر يفتح «اختيار من الكتالوج العام»، يختار التعريف ويحدد سعره. ينشأ عرضه بحالة غير متاح حتى يفعّله صراحةً. لا ينسخ سعر المتجر المصدر أو عمولته.
4. إذا كان لدى التاجر سجل قديم للمنتج نفسه، يختاره من «ربط بسجل قائم في متجري» بدل إنشاء عرض جديد. تحفظ المعاملة معرفه وسعره وتوفره وتربطه بالتعريف العام. لا يمكن ربط سجل من متجر آخر أو سجل مربوط بتعريف مختلف.
5. تربط معاملة ذرية المنتج العام بالمتجر. إعادة الضغط أو إعادة المحاولة أو الاختيارات المتزامنة تعيد عرض المتجر نفسه دون إعادة ضبط سعره أو إنشاء نسخة ثانية.
6. الأرشفة تخص عرض المتجر وحده. الاستعادة لا تتيح البيع تلقائيًا ولا تمس عروض المتاجر الأخرى.
7. صفحات الكتالوج العام 50 سجلًا، وعروض التاجر 100 سجل في الصفحة مع تحميل المزيد؛ البحث في الواجهة يصرّح بأنه ضمن المنتجات المحملة.

تظل المنتجات القديمة ظاهرة لأصحابها حتى تراجعها الإدارة. إنشاء تعريف جديد من لوحة التاجر القديمة `save-product` مرفوض؛ مسار الإدارة لإنشاء منتج جديد ما زال قائمًا، ثم يُعتمد في الكتالوج العام. ربط سجل قديم واحد متاح في الواجهة؛ دمج سجلين قديمين مختلفين للمتجر نفسه يحتاج أداة مراجعة/دمج مستقلة قبل حذف أي تكرار تاريخي.

## الصلاحيات والتوافق

- واجهات القراءة والربط تمر عبر API الخادم الموجود، دون إضافة وظيفة Vercel أو توسيع `firestore.rules`.
- هوية المتجر من عضوية `staff` الموثوقة، لا من `storeId` يرسله المتصفح.
- يعيد الخادم فحص المدير والتعطيل وإلغاء الجلسة داخل معاملة الربط. مسؤول التحضير لا يربط منتجات أو يعدل الأسعار.
- اعتماد تعريف عام للإدارة فقط، مع إعادة فحص صلاحيتها داخل المعاملة وسجل تدقيق.
- لا تُرجع قائمة الكتالوج العام بيانات المتجر المصدر أو سعره أو عقده؛ الخيارات تُسقط إلى الحقول المعتمدة فقط.
- لا يوجد في هذه الدفعة تعديل عام متزامن لتعريف منشور أو نظام مراجعة مسودات. لذلك لا يجوز تعديل حقول التعريف داخل عرض مرتبط؛ تبقى الأسعار والتوفر والأرشفة مستقلة.

## حدود التحقق

الاختبارات الخدمية تستخدم قاعدة ذاكرة تختبر المعاملات والتزامن والصلاحيات. اختبار Chromium يستخدم المكوّن الحقيقي مع ردود API اختبارية، ولا يثبت صلاحيات قاعدة إنتاجية أو ترحيل بيانات فعلية. أُضيف مسار الاعتماد والربط إلى اختبار Firebase التكاملي القائم ليعمل في CI.

لم نقرأ قاعدة الإنتاج أو نُرحّل منتجات فعلية: أمر سرد قواعد Firestore تعذر بسبب غياب جلسة CLI مخولة. محاكي الاختبارات الحالي Standard وفق سجلات CI؛ إصدار قاعدة الإنتاج لم يتحقق في هذه الجلسة. لا ننشئ قاعدة أخرى أو نبدل الإصدار. اعتماد المنتجات الفعلية يتم من واجهة الإدارة بعد النشر وبصلاحياتها الحالية.
