# نقل سنجوب إلى Supabase — المرحلة الأولى

هذه مرحلة تجهيز واختبار، وليست تحويلًا للتطبيق. Firebase ما زال مصدر الإنتاج والمصادقة. لا تنفذ التحويل النهائي بهذا المخطط وحده.

## ما تم تجهيزه

- مخطط PostgreSQL للمنتجات والتصنيفات الهرمية والعبوات وعروض التجار والصور والخيارات.
- أسعار صحيحة بالقروش، وعملة EGP؛ باركود فريد عند وجوده، وعرض واحد لكل متجر وعبوة، ومفتاح صنف داخلي للتاجر فريد داخل متجره.
- مجموعات خيارات مستقلة عن العبوات، وصورة عامة وصورة عبوة وصورة خاصة بعرض التاجر.
- profiles تحتفظ بمعرّف Firebase وتتيح ربط auth.users لاحقًا بمعاملة خادم موثوقة. لا يوجد ربط تلقائي بالبريد ولا استيراد كلمات مرور.
- RLS مفعّل بلا سياسات إتاحة، وصلاحيات anon/authenticated مسحوبة عمدًا حتى تنفيذ المصادقة. المخطط غير جاهز لاتصال الواجهة.
- تصدير إداري شامل للمجموعات المكتشفة والمجموعات الفرعية، حتى إذا كان المستند الأب محذوفًا. يُحفظ المسار مع أنواع Firestore دون إسقاط دقة timestamp أو المراجع أو البايتات.
- تجهيز SQL لاستيراد النسخة إلى migration_private فقط، مع بصمة SHA256 وعدد السجلات ومعاملة واحدة وإمكانية إعادة الاستيراد دون مضاعفة السجلات. هذه نسخة مرحلية، لا تحول البيانات إلى الجداول التجارية تلقائيًا.

## الجرد الأولي من الكود

| المجال | أمثلة المصادر | المعالجة المطلوبة |
|---|---|---|
| الهوية والصلاحيات | users, admins, staff, accountAccess | حفظ UID، نقل الأدوار من مصادر الخادم، وحفظ التعطيل وإلغاء الجلسات |
| التجارة | stores, products, catalogProducts, catalogOffers | ربط الصنف والعرض دون دمج بالاسم؛ الحفاظ على معرفات العروض القديمة |
| الطلبات | orders, fulfillments, preparationQueue, courierAssignments | جداول طلبات وبنود وعمليات تنفيذ، إسقاط خاص بكل متجر، ولقطات أسعار تاريخية |
| المال | merchantContracts, merchantSettlements, settlementClaims، سجلات الدفع | تسوية الأعداد والمبالغ قبل الإتاحة، وعدم إعادة تنفيذ تحصيل أو تحويل |
| العنوان والتوصيل | بيانات المستخدم، tracking، orderSecrets | فصل البيانات الحساسة والرموز عن القراءة العامة |
| الإدارة والمحتوى | auditLogs, notifications, appConfig, promotions, coupons، طلبات الانضمام | سياسات مخصصة وسجل تدقيق وحماية العمليات |
| إشارات التشغيل | storeOrderSignals, courierOrderSignals، سجل طلبات العميل | تقييم إعادة بنائها من البيانات الأصلية بدل جعلها مصدر الحقيقة |

هذا جرد من الكود، وليس قائمة مؤكدة بكل المجموعات الموجودة في الإنتاج. التصدير يكتشف الموجود فعليًا ويضع أعداد كل مسار مجموعة في manifest. لا تنشر هذا الملف؛ أسماء المسارات قد تتضمن معرّفات مستخدمين.

## المتطلبات قبل الاتصال

يلزم رابط Supabase، واتصال PostgreSQL بصلاحيات تطبيق المخطط، وبيانات Firebase Admin للقراءة. لم تُضف أسرار إلى المشروع. مفاتيح REST وحدها لا تنشئ مخطط SQL. استخدم بيئة أسرار أو اتصالًا إداريًا موثوقًا، ولا تضع رابط قاعدة يتضمن كلمة مرور في Git أو سجل الأوامر.

## خطوات النقل المرحلي

1. أخذ نسخة احتياطية من Firebase وتحديد ما إذا كانت البيانات تجريبية أم يجب الحفاظ عليها بالكامل. الحفاظ هو الافتراض.
2. إيقاف الكتابات من الويب والموبايل والخوادم والمهام المجدولة خلال التصدير؛ الأداة لا تفرض الإيقاف ولا توفر لقطة متزامنة أثناء الكتابات. إعداد المتغير أدناه إقرار من المشغّل بعد الإيقاف الفعلي.
3. باستخدام متغيرات FIREBASE_PROJECT_ID وFIREBASE_DATABASE_ID وبيانات Admin أو ADC الموثوقة:

```sh
MIGRATION_WRITES_PAUSED=true node scripts/migration/export-firestore.mjs /tmp/sangoub-private-export
node scripts/migration/prepare-import.mjs /tmp/sangoub-private-export /tmp/sangoub-private-import.sql
```

المجلد والملف الناتجان يجب ألا يكونا موجودين سابقًا. يحفظان بصلاحيات خاصة. لا يقرأ المصدّر .env.local تلقائيًا لتجنب تصدير مشروع المحاكاة بالخطأ. الملف قد يتضمن بيانات شخصية وأسرار طلبات: احفظه مشفرًا عند النقل والتخزين طويل المدى. الصور الفعلية وحسابات Firebase Auth خارج تصدير Firestore؛ يلزمان جردًا ونسخًا منفصلين. لا تغيّر روابط الصور قبل التحقق من الملفات.

4. تطبيق migration على Supabase تجريبي باستخدام اتصال SQL إداري، ثم تطبيق ملف الاستيراد مع ON_ERROR_STOP. لا تطبقهما على قاعدة لها جداول متعارضة دون مراجعة.
5. التحقق من بصمة المصدر وعدد المستندات وتوزيع المسارات. جداول التجارة ستظل فارغة في هذه المرحلة؛ لا يعتبر نجاح استيراد staging نجاح تحويل التطبيق.
6. المرحلة التالية: محوّلات صريحة لكل مجال، تقرير استثناءات للتعارضات والأسعار والعلاقات، وحفظ خرائط المعرفات. لا تخمين وزن من الاسم ولا دمج أصناف متشابهة تلقائيًا.
7. استكمال الطلبات والمال والصلاحيات، ثم مصادقة البريد وسياسات RLS وعقود API والاشتراكات، واختبار عزل المتاجر والعميل والمندوب.
8. إعادة تجربة النقل كاملة، ثم نافذة تحويل نهائية وقرار رجوع. بعد قبول كتابات في القاعدة الجديدة، الرجوع يتطلب نقل تلك الكتابات أيضًا؛ ليس تبديل متغير فقط.

## حدود المرحلة

لا توجد كتابة إلى Supabase الفعلي أو قراءة إنتاج Firebase دون بيانات الاتصال. لم تُنقل الحسابات أو الصور أو الطلبات، ولم تتغير firestore.rules أو واجهات تسجيل الدخول. لا تستخدم service/secret key في المتصفح. اختبارات PostgreSQL المضمنة تتحقق من SQL والقيود والرفض الافتراضي، ولا تثبت إعداد مشروع Supabase الخارجي أو سياسات لم تُكتب بعد.
