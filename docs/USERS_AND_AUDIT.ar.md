# إدارة المستخدمين وسجل التدقيق

قسم `المستخدمون` على `/admin#users` يتعامل مع Firebase Authentication الحقيقي وملفات Firestore والأدوار الموثوقة. قسم `/admin#audit` يعرض سجل التدقيق. لا توجد حسابات أو أرصدة أو أحداث افتراضية.

## المستخدمون

- عرض الحسابات بصفحات من 50 حسابًا، والبحث في جميع الحسابات بالبريد الكامل أو UID. يظهر الدور الفعلي من `admins` أو `staff`، ولا يمنح `users.role` وحده صلاحية.
- إنشاء حساب بريد بكلمة مرور عشوائية لا تُعرض ولا تُحفظ في Firestore. لإنشاء كلمة مرور يختارها صاحب الحساب، استخدم «استعادة الوصول» وسلّمه الرابط الخاص. التوثيق مطلوب؛ لا يضع المدير علامة توثيق مزيفة.
- تعديل الاسم والبريد وبيانات الاتصال والوزارة والمكتب، وتعيين موظف أو شيف بمتجر محدد أو مندوب أو مدير. الرصيد المالي غير قابل للتعديل الحر.
- تعطيل/تفعيل الحساب وإلغاء جلساته. تعطيل الحساب يزيل عضوية الإدارة والفريق. التفعيل لا يستعيد الصلاحيات السابقة؛ يجب تعيينها صراحة.
- تغيير الدور وإلغاء الجلسات يفرضان تسجيل دخول جديد. حماية `accountAccess/{uid}` في القواعد تمنع استعمال ID token مخزّن بعد التعطيل أو الإلغاء، حتى قبل انتهاء صلاحيته الطبيعي.
- لا يسمح للمدير بتعطيل نفسه أو تغيير دوره أو حذف نفسه أو إلغاء جلساته من نفس الجلسة. تُسلسل عمليات عضوية الإدارة لمنع إزالة المديرين بالتزامن.
- الطلبات النشطة المرتبطة بالعميل أو المندوب أو مطبخ الشيف تمنع تغيير دوره أو تعطيله أو حذفه حتى إعادة تعيينها أو إغلاقها.
- الحذف يمنع عند وجود رصيد غير مسوّى، ويتطلب كتابة UID والسبب؛ يحذف حساب الدخول ويمسح بيانات الاتصال والعنوان من ملفه. يبقى UID والطلبات والرصيد التاريخي وسجل التدقيق لأغراض التشغيل والتسوية. هذا ليس حذفًا شاملًا لكل البيانات التاريخية.

## سجل التدقيق

- الحقول: `actorUid`, `actorEmail`, `action`, `entityType`, `entityId`, `before`, `after`, `changedFields`, `reason`, `createdAt`, `status`, `source`، و`completedAt` و`errorCode` عند الحاجة، و`request` لمعرف الطلب والمتصفح وعنوان الاتصال عند توفره.
- يتضمن فتح مساحة الإدارة وتسجيل الخروج وتعديلات الإدارة عبر `/api/admin-users` و`/api/admin-data` للمتاجر والمنتجات والطلبات والفريق والخصومات ومراجعات الشراكات والتوظيف واعتماد متجر جديد. إنشاء الطلب عبر `/api/orders` وتسليمه عبر `/api/order-delivery` مسجلان أيضًا. إصدار إذن رفع R2 مسجل كإذن فقط، وليس تأكيد رفع الملف، وحذف الصورة له حالة تنفيذ.
- معاملة تعديل Firestore تتضمن حدث التدقيق نفسه؛ يفشلان أو ينجحان معًا. الكتابة المباشرة من عميل المدير إلى المجموعات المغطاة ممنوعة بالقواعد الجديدة.
- عمليات Authentication تبدأ بسجل `pending` وقفل للحساب، وتجمّد صلاحية الحساب مؤقتًا أثناء تغييرات الوصول الحساسة، ثم `success` أو `failed` أو `partial`. محاولات المدير المرفوضة قبل التنفيذ تُسجل كـ`blocked` مع التغيير المطلوب، دون اعتباره تغييرًا حدث بالفعل. لا توجد معاملة ذرية مشتركة بين Authentication وFirestore؛ السجل يوضح هذه الحقيقة.
- لا يستطيع عميل الويب إنشاء السجل أو تعديلَه أو حذفَه. الخادم يكمل حالة العملية المعلّقة مرة واحدة. مسؤول Firebase ذي صلاحيات IAM يستطيع الوصول خارج التطبيق؛ هذا ليس نظام تخزين WORM أو توقيعًا تشفيريًا ضد مسؤول المشروع.
- لا تُحفظ كلمات المرور أو ID tokens أو أسرار OTP أو روابط إعادة الضبط أو روابط الرفع الموقّعة في التدقيق.
- الفلاتر: مطابقة واحدة للمنفّذ أو بريده أو العملية أو المجموعة أو السجل أو حالة التنفيذ، مع نطاق زمني. الصفحات مرتبة بالتوقيت وبمؤشر Firestore. تصدير JSON يجلب جميع صفحات النتائج المطابقة، ويمكن إلغاؤه، وتسجل عملية التصدير نفسها.
- التحديث كل 30 ثانية للصفحة الأولى. الأوقات المعروضة بتوقيت القاهرة، ومدخلات النطاق الزمني بتوقيت جهاز المستخدم.
- **نطاق التغطية:** يبدأ من تفعيل الإصدار؛ لا يسترجع تاريخًا سابقًا ولا يرصد تغييرات Firebase Console أو كل كتابات Flutter المباشرة (مثل تعديلات ملف الموظف، تحضير الشيف، تتبع GPS). يلزم نقل هذه المسارات إلى خادم مدقّق أو تفعيل مراقبة قواعد البيانات السحابية لتغطية جميع قنوات المنصة. لا تعرض هذه النسخة هذه الأحداث كأنها مسجلة.

## النشر والتفعيل

1. انشر أحدث `main` في Vercel. واجهات الخادم تحتاج `FIREBASE_PROJECT_ID=capital-talabat` و`FIREBASE_DATABASE_ID=(default)` و`FIREBASE_CLIENT_EMAIL` و`FIREBASE_PRIVATE_KEY` بصلاحيات Firebase Authentication وFirestore المناسبة. الأسرار للخادم فقط؛ لا تستخدم بادئة `VITE_`.
2. من جهاز مسجّل في Firebase CLI، داخل أحدث نسخة من المستودع، نفّذ:

```bash
npx --yes --package firebase-tools firebase deploy --only firestore --project capital-talabat
```

هذا ينشر القواعد والفهارس الجديدة في `firestore.indexes.json`. انتظر اكتمال إنشاء فهارس `auditLogs` قبل استعمال فلاتر السجل.
3. اختبر بحساب مدير حقيقي: أضف مستخدمًا، عدّل دوره، عطّله، ثم تحقق من الأحداث وتفاصيل قبل/بعد. لا تشارك روابط إعادة الضبط أو المفاتيح في المحادثات.

## مراجعة الفشل الجزئي

إذا ظهر `partial`، لا تتجاوز القفل بتكرار العملية. استخدم `auditLogs/{operationId}` و`adminUserLocks/{uid}` لتحديد العملية. قارن حساب Authentication مع `users/{uid}` و`staff/{uid}` و`admins/{uid}` و`accountAccess/{uid}`. لا ترفع علامة `accountAccess.operationLocked` حتى تراجع الحالة؛ هي تمنع الحساب من استخدام صلاحيات قديمة أثناء نتيجة غير مؤكدة. أصلح الحالة المقصودة باستخدام اتصال إداري موثوق وسجّل التصحيح. بعد التأكد، أزل قفل المستخدم، وإذا كان `adminControl/membership.operationId` هو نفس معرف العملية، أزل قفل العضوية كذلك. لا تُحذف الأقفال تلقائيًا بمؤقت قد يسمح لعمليتين متعارضتين بالعمل معًا.

## الاختبار

`npm run test:rules` يتضمن اختبارات حسابات Auth فعلية داخل المحاكيات وقواعد منع العبث بالتدقيق والتعطيل. `npm run test:admin-web` يختبر إنشاء حساب وتغيير دوره وتعطيله والتصدير من الواجهة، بالإضافة إلى شاشات الإدارة على الموبايل والتابلت والكمبيوتر. جميع بيانات هذه الاختبارات في مشروع demo محلي معزول.
