## ما تحقق من السجل والكود

السجل المرفق يخص `feature/osm-tracking@9b3c18c`. بناء Vite نجح؛ أخطاء TS2688 ظهرت في تجهيز وظائف Vercel بسبب توريث أنواع الواجهة `vite/client` و`vite-plugin-pwa/client`. السجل ينتهي عند Deploying outputs، لذلك لا نستنتج منه فشل النشر النهائي أو نجاح تشغيل API.

أضيف `api/tsconfig.json` للـserverless بأنواع `node` بدل أنواع Vite، مع بقاء إعداد الواجهة. `lint:server` وCI يفحصانه. اختبار الوظائف المترجمة أصبح يستخدم الإعداد نفسه مع `noCheck:false`، ويشمل `/api/osm/[action]`؛ اختبار Node الأصلي يشمله أيضًا. استبدل parameter property في OsmError بصيغة يدعمها strip-types. لم تُضف مكتبة أو تتغير إصدارات dependencies.

## مصدر GPS وشاشاته

| الطرف/الرابط | الناشر أو القارئ الفعلي | حدود البيانات |
| --- | --- | --- |
| المندوب `/courier` | `CourierTracking` → `useCourierTracking` → sharedLocationSource/trackingSession → `tracking/{id}` | المندوب المعيّن في with_courier فقط؛ عقد coordinates/active/updatedAt ثابت |
| العميل، الإيصال | `OrderMap` و`useOrderTracking` و`trackingObserver` | وثيقة طلب صاحب الحساب وفق القواعد الحالية |
| `/track?orderId=...` و`/order-tracking/{id}` | نفس الإيصال والمكوّن السابق؛ `/track` دون id يعرض طلبات الحساب | لا صفحة مجهولة تكشف بيانات أو طلبًا تلقائيًا من حساب آخر |
| التاجر `/merchant`، تبويب التتبع | نفس OrderMap/TrackingMap/observer، عبر `merchant-tracking` في operations | مراجعة كل10s أثناء فتح تفاصيل طلب واحد؛ ACL transaction حسب staff.storeId وorder.storeIds؛ لا عنوان عميل أو منتجات متجر آخر |
| الإدارة | OrderMap وCouriersLiveMap | الصلاحيات الحالية؛ خرائط محدودة بالطلبات النشطة، دون مواقع افتراضية |

الموقع المنشور واحد للمندوب لكل طلب، والتاجر لا ينشر موقعًا جديدًا ولا يقرأ tracking مباشرة. يستخدم server projection حتى لا نفتح قواعد Firestore للتجار أو نكشف parent order. مصادر عرض العميل/الإدارة listeners لحظية، والتاجر polling10s وليس بثًا لحظيًا. هذا فرق صريح في النقل، مع توحيد البيانات والحالة والخريطة.

## الدقة والتوقف والصلاحيات

- Filter الأصلي لم يتغير: قراءة جيدة ≤30m، وقد يقبل ≤100m بعد تأخر60s؛ حدود السرعة/المسافة موجودة أصلًا. تعرض واجهة المندوب ±دقة القراءة المقبولة، دون إرسال accuracy كحقل جديد.
- مؤقت heartbeat يفحص كل10s، لكن filter ينشر heartbeat كل60s عند الوقوف؛ ليست كتابة كل10s. بعد120s دون GPS موثوق لا يستمر heartbeat في الادعاء بموقع حي. أخطاء GPS تحاول inactive، وزر إعادة التشغيل لا يغني عن إذن الموقع الصحيح.
- أول snapshot مؤكد لا يُعد دليل بث حي؛ نعرضه كنقطة أخيرة غير مؤكدة حتى وصول revision جديد. يمنع ذلك عرض وثيقة تاريخية قديمة كتتبع حي. قد ينتظر المستخدم heartbeat عند وقوف المندوب.
- inactive أو فقد القراءة يزيل marker الحي والمسار؛ النقطة القديمة المعروضة عند الانقطاع باهتة. تغيير المستخدم/الطلب يمنع ظهور snapshot سابق في الإطار الجديد.
- تغيير المندوب عبر admin-data يحذف tracking القديمة في transaction التعيين نفسه، ولا يغيّر شكل الطلب. لم يُختبر هذا التعديل على emulator بسبب عائق التنزيل السابق؛ يلزم اختبار إعادة تعيين متزامن قبل الإطلاق.
- proxy OSM أصبح يفحص الحساب المؤكد والقفل/إلغاء الجلسة عبر operationIdentity، لا token وحده.
- لا تعديل أو نشر لـfirestore.rules. لا Flutter/Android أو منطق دفع/سلة. تعديلات ShopFront وApp تخص وصول شاشة التتبع فقط.

## التحقق

نجحت محليًا: lint، lint:server،85 اختبارًا عامًا،10 اختبارات native API،اختبار compiled API،4 اختبارات portal،build،fixture الخريطة320/390/1366 مع حجب الشبكة الخارجية. اختبار الخريطة يثبت إزالة marker والمسار عند حذف النقطة أيضًا. النتائج الحرفية في TRACKING_WORKLOG.md.
