# ربط الموبايل بدورة التشغيل وإدارة واجهة العميل

الويب والخادم منفذان في هذا التحديث. ملفات Flutter لم تتغير. هذه واجهات جاهزة لمساعد الموبايل؛ لا يعني نشر الويب أن واجهات التحضير والمندوب والسلايدر داخل التطبيق تغيرت تلقائيًا.

## الدخول وتحديد واجهة الحساب

1. الدخول عبر Firebase Authentication بالحساب الحقيقي: البريد وكلمة المرور، أو Google، أو الهاتف إذا كان المزود مفعّلًا بالفعل في المشروع.
2. أرسل Firebase ID token في `Authorization: Bearer <idToken>` إلى واجهات POST. لا ترسل UID أو دورًا باعتبارهما إثبات صلاحية، ولا تضع مفاتيح الخادم في التطبيق.
3. بعد الدخول: `POST /api/operations` مع `{ "action": "profile" }`.
4. استجابة `destination` تحدد الشاشة: `customer_home` للعميل، `store_preparation` لفريق المتجر، `courier_tasks` للمندوب، و`admin_web` للإدارة.
5. `needsVerification: true`: اطلب توثيق البريد عبر Firebase SDK ثم أعد تحميل الحساب والتوكن. لا تفتح مهام التشغيل قبل التوثيق.
6. `requiresStoreAssignment: true`: اعرض رسالة ربط الحساب بمتجر بواسطة الإدارة. لا تعرض قائمة اختيار متجر تمنح الوصول لمتجر آخر.

`role` الحالي لفريق المتجر يظل `restaurant` للتوافق؛ `duty` إما `preparer` أو `manager`. `store.preparationType` إما `kitchen` أو `picking` حسب نشاط المتجر. الحسابات القديمة التي لا تحتوي `duty` تُعامل كمسؤولي متجر للحفاظ على التوافق؛ راجع المهمة وأعد حفظها صراحة من الإدارة. الحسابات الجديدة الافتراضية `preparer` لا تعدّل الأسعار أو حالة المتجر مباشرة؛ `manager` يدير كتالوج متجره. لا يلزم إنشاء تطبيق مستقل لكل دور؛ اعرض واجهته داخل التطبيق بحسب الاستجابة الموثوقة.

الإدارة تنشئ حساب التشغيل من صفحة المستخدمين وتحدد المتجر والمهمة. يظهر رابط خاص لتعيين كلمة المرور مرةً بعد الإنشاء، ويسلمه المدير لصاحب الحساب فقط. لا توجد كلمة مرور مشتركة، ولا يثبت امتلاك الرابط توثيق البريد تلقائيًا. عند تغيير الصلاحية أو إلغاء الجلسات، يلزم تسجيل الدخول مجددًا. تعطيل الحساب يمنع واجهات التشغيل.

## تفعيل آمن ومتدرج

- الافتراضي: تبقى الطلبات الجديدة على الفلو الحالي. لا تعاد كتابة طلبات قديمة.
- قبل التفعيل: انشر `firestore.rules`، واربط واختبر شاشات Flutter المذكورة هنا على بيئة تجريبية.
- بعد اكتمال المتطلبات، اضبط `OPERATIONS_V2_READY=true` في إعدادات خادم Vercel وأعد النشر. هذا المتغير غير سري، ولا يكفي وحده لتفعيل الطلبات الجديدة.
- من الويب: «واجهة التطبيق والحملات» ← «تفعيل تذاكر المتاجر وتأكيد استلام كل نقطة».
- يلزم الشرطان: متغير الجاهزية وإعداد الإدارة. عندها فقط ينشئ `/api/orders` طلبات تحمل `fulfillmentVersion: 2` وتذاكر المتاجر في المعاملة نفسها.
- إيقاف الإعداد يوقف إدخال طلبات جديدة في الدورة الجديدة؛ الطلبات القائمة تستكمل عبر واجهاتها.
- احتفظ بمسار التشغيل القديم للطلبات التي لا تحتوي `fulfillmentVersion: 2` حتى إغلاقها. القائمة الجديدة تعرض طلبات الدورة الجديدة فقط.

## كل طلبات التشغيل عبر POST /api/operations

الاستجابات الفاشلة JSON بحقل `error` عربي: 401 جلسة منتهية، 403 صلاحية/حساب غير موثق، 400 بيانات ناقصة، 409 حالة تغيرت أو شرط تشغيل غير مكتمل. حدّث القائمة عند 409 ولا تعاود تنفيذ العملية بلا نهاية.

### قائمة المهام

```json
{ "action": "list", "cursor": "optional-nextCursor" }
```

يُشتق متجر التحضير أو تكليف المندوب من الجلسة. الاستجابة `{ items, nextCursor }` حتى 50 مهمة في الصفحة. مرر `nextCursor` كما هو للصفحة التالية. حدّث القائمة دوريًا عند ظهور الشاشة وعند الرجوع إليها؛ لا تشغل polling في الخلفية.

فريق المتجر يستقبل تذكرته فقط: `orderId`, `orderNumber`, `storeId`, `storeName`, `preparationType`, `items`, `status`, `checkedItemIds`, `issueOpen`, `issue`, و`paymentReady`. لا تحتوي استجابته عنوان العميل أو هاتفه أو أصناف متجر آخر.

المندوب يستقبل الطلبات المكلّف بها فقط: رقم الطلب، حالة التوصيل، بيانات العميل والعنوان، الدفع و`amountToCollect`، ومصفوفة `stops`. كل نقطة تحتوي منتجات المتجر وحالته وموقع الاستلام وتأكيدات الاستلام.

### التحضير ومراجعة الأصناف

```json
{ "action": "prepare", "orderId": "...", "next": "preparing" }
```

ثم بعد مراجعة كل الأصناف وكمياتها:

```json
{
  "action": "prepare",
  "orderId": "...",
  "next": "ready",
  "checkedItemIds": ["item-0", "item-2"]
}
```

استخدم معرفات `items[].id` الفعلية الواردة في التذكرة؛ لا تفترض تسلسلًا يبدأ من الصفر داخل كل متجر. يلزم مراجعة جميع عناصر التذكرة دون تكرار معرفات. لا يحتاج الحساب إرسال متجره، ولو أرسل متجرًا مختلفًا يُرفض الطلب.

إعادة نفس الحالة آمنة عند ضياع الاستجابة، لكن لا يمكن القفز من جديد إلى جاهز. لا يصبح الطلب كله جاهزًا حتى تجهز جميع تذاكر المتاجر. لا يغير التحضير أسعار أصناف الطلب.

### الإبلاغ عن نقص أو مشكلة

```json
{ "action": "report-issue", "orderId": "...", "reason": "الكمية غير متاحة وتحتاج مراجعة" }
```

تظهر المشكلة في شاشة إشراف الإدارة، ويُمنع استمرار التحضير أو استلام التذكرة حتى تسجيل المعالجة. لا يتم استبدال منتج أو تعديل سعر تلقائيًا. تسجل الإدارة المراجعة بإجراء `resolve-issue` مع `orderId`, `storeId`, و`reason`؛ فريق المتجر لا يملك هذا الإجراء.

### استلام المندوب من كل نقطة

الإدارة تعيّن المندوب من سجل الطلبات بعد جاهزية الجميع. يظل الطلب `ready`؛ التعيين ليس استلامًا.

```json
{ "action": "pickup", "orderId": "...", "storeId": "...", "confirmed": true }
```

قبل التأكيد، اعرض الأصناف والكميات والأكياس/الملاحظات واسم المتجر للمندوب. لكل نقطة حالة مستقلة. يرفض الخادم استلام متجر غير جاهز أو غير تابع للطلب، أو الاستلام بواسطة مندوب غير مكلّف. بمجرد بدء الاستلام لا تسمح الواجهة بإعادة تعيين المندوب؛ الخادم يفرض ذلك أيضًا.

بعد استلام الجميع:

```json
{ "action": "depart", "orderId": "..." }
```

عندها فقط تصبح الحالة `with_courier`. أظهر تتبع الطريق للعميل اعتمادًا على الحالة المحفوظة، وليس مجرد ضغط زر التكليف.

### التسليم

الواجهات الحالية مستمرة:

- العميل: `POST /api/order-delivery` مع `{ action: "code", orderId }` للحصول على رمزه الخاص.
- المندوب: `{ action: "deliver", orderId, otpCode, collectedAmount }` على الواجهة نفسها.

في الطلب النقدي يلزم تطابق المبلغ المحصل مع الإجمالي، مع تأكيد كل نقاط الاستلام. الطلب الإلكتروني يتطلب `paymentStatus: paid` و`paymentConfirmedAt` صادرتين عن تأكيد موثوق، ويكون `collectedAmount: 0`.

**حد قائم:** مسار callback الحالي لجيديا لا يتحقق من إشعار السداد تحققًا موثوقًا. لذلك لا يُسمح له بتأكيد دفع طلبات الدورة الجديدة؛ تعود `PAYMENT_VERIFICATION_REQUIRED`. الدورة الجديدة النقدية مختبرة، ولا يُفعّل الدفع الإلكتروني فيها حتى استكمال التحقق من مزود الدفع. اختيار وسيلة دفع إلكترونية وحده لا يجعل الطلب مدفوعًا.

### إلغاء العميل

```json
{ "action": "cancel", "orderId": "..." }
```

لصاحب الطلب فقط وقبل بدء التحضير؛ يُغلق الطلب وكل تذاكره وقوائمه معًا. الطلبات الجديدة لا تُحدّث مباشرة من Firestore. بعد بدء التحضير، وجه العميل للإدارة لمراجعة الطلب بدل إلغاء جزئي غير متسق.

## واجهة العميل والحملات

`GET /api/app-content` عام، ولا يحتاج جلسة. استجابة `schemaVersion: 1` تحتوي:

```json
{
  "schemaVersion": 1,
  "config": {
    "sections": [
      { "type": "slider", "enabled": true },
      { "type": "offers", "enabled": true },
      { "type": "stores", "enabled": true },
      { "type": "products", "enabled": true }
    ],
    "sliderMode": "automatic",
    "maxSlides": 6
  },
  "slides": [
    { "id": "...", "title": "...", "subtitle": "...", "imageUrl": "https://...", "targetType": "product", "targetId": "..." }
  ]
}
```

- اعرض الأقسام المفعلة بترتيب المصفوفة. لا تعطل بيانات المتاجر نفسها عند إخفاء قسم المتاجر؛ المنتجات تظل مرتبطة بها للتشغيل.
- الأهداف المسموح بها: `product` يفتح تفاصيل المنتج، `store` يفتح منتجات المتجر، و`offers` يفتح صفحة العروض.
- الوضع التلقائي يختار من المنتجات المخفضة المتاحة المرتبطة بمتجر مفتوح ولها صورة HTTPS، بحد قراءة 500 منتج متاح. الحملات اليدوية محدودة بحد أقصى 100 حملة، وتُرتب حسب الأولوية ثم المعرف.
- لا تعرض banner ثابتًا يوحي بخصم عند خلو `slides`. اخف السلايدر أو استخدم مادة تعريفية واضحة.
- حملات المنتجات تُستبعد إن لم يعد المنتج مخفضًا أو متاحًا أو كان متجره مغلقًا. لا تُنسخ الأسعار من الحملة لحساب الطلب.
- إعداد المواعيد في الويب بتوقيت القاهرة، والتخزين بصيغة ISO UTC. انتهاء الحملة يخفي الإعلان ولا يعيد تسعير المنتج.
- الرد العام قد يُخزن حتى نحو دقيقة في CDN. أعد التحقق من السعر والتوافر عند فتح المنتج وإتمام الطلب؛ الخادم يحسب الأسعار بنفسه.
- عند فشل قراءة الإعدادات استخدم واجهة افتراضية قابلة للعمل، دون اختراع حملات أو إظهار قسم فارغ بحجم كبير.

## مسارات البيانات المحمية

- `orders/{orderId}/fulfillments/{storeId}`: تذاكر المتاجر.
- `stores/{storeId}/preparationQueue/{orderId}`: مؤشرات القائمة النشطة للمتجر.
- `courierAssignments/{uid}/orders/{orderId}`: مؤشرات التكليف النشطة.
- `appConfig/customerHome`, `appConfig/operations`, `promotions/{id}`: إعدادات الإدارة.

هذه المسارات لا تُقرأ أو تُكتب مباشرة من SDK العميل؛ استعمل الواجهات أعلاه. هذا يمنع قراءة المستند الكامل الذي يحتوي أصناف تجار آخرين أو بيانات عميل لا يحتاجها الشيف.

## اختبار التسليم بين المساعدين

1. إنشاء حساب مطعم وحساب سوبر ماركت وحساب مندوب من الإدارة؛ تعيين كلمة المرور وتوثيق الحسابات.
2. طلب نقدي من المتجرين؛ كل حساب تحضير يرى أصنافه فقط.
3. رفض الجاهزية قبل مراجعة جميع الأصناف، وتجربة نقص صنف ثم معالجته إداريًا.
4. تعيين مندوب، ورفض بدء الطريق قبل تأكيد نقطتي الاستلام، ورفض مندوب آخر.
5. تأكيد التسليم بالرمز والمبلغ الصحيحين وإغلاق قوائم التشغيل.
6. تبديل ترتيب الأقسام والحملات من الويب وملاحظة الموبايل، مع تجربة انتهاء الحملة وإيقاف المنتج.
7. تشغيل طلبات قديمة بالتوازي للتأكد من استمرار التوافق.

## إعدادات مزودي الدفع والرسائل

أُزيلت قيم كلمات مرور الدفع ومفتاح الرسائل الثابتة من الكود. استخدم متغيرات Vercel السرية `GEIDEA_API_PASSWORD` و`GEIDEA_TEST_API_PASSWORD` و`CHATAMAN_API_KEY` عند الحاجة، ولا تضعها في Flutter أو في متغيرات `VITE_`. القيم التي سبق حفظها في المستودع تحتاج تدويرًا لدى المزود؛ حذفها من آخر نسخة لا يلغيها من التاريخ. لا تعلن اكتمال الدفع الإلكتروني قبل تنفيذ تحقق موثوق من جهة الخادم.
